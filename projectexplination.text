1. PROJECT OVERVIEW
================================================================================

--------------------------------------------------------------------------------
1.1 BUSINESS OBJECTIVE
--------------------------------------------------------------------------------

Prime Fresh ERP is a full-scale Enterprise Resource Planning system built
specifically for the fresh produce and agri-supply-chain industry in India.
The system digitalises and automates the end-to-end lifecycle of fresh produce —
from the point of procurement (farm or vendor) all the way through quality
checking, inward registration, stock management, sales dispatch, invoicing,
and financial voucher management.

The platform manages four group companies simultaneously:
  - Prime Fresh Limited
  - Florens Fresh Supply Solutions Pvt. Ltd.
  - Florens Farming Private Limited
  - Prime Fresh Retail (I) Private Limited

Core business objectives:
  a) Eliminate paper-based procurement and approval processes by digitising
     every document (RFPA, Deal Slip, GRN, AQR, Inward Register, Invoices, etc.)
  b) Enforce structured multi-level approval workflows so no document moves
     forward without authorised sign-off.
  c) Provide real-time inventory visibility across all branches and warehouses.
  d) Track payments (paid/unpaid) against goods receipts and invoices.
  e) Generate actionable dashboards for procurement, sales, and management teams.
  f) Maintain complete audit trails of every user action, approval step,
     and document state change.
  g) Support compliance with Indian tax requirements — GST (CGST/SGST/IGST),
     invoice formats, and IST (Asia/Kolkata) timestamps throughout.

--------------------------------------------------------------------------------
1.2 USERS
--------------------------------------------------------------------------------

The system supports the following user roles, each with distinct permissions:

  ADMIN
    - Full system access across all companies and branches
    - Can create/manage employees, configure approval flows, manage roles
    - Access to all dashboards, reports, and system settings

  EMPLOYEE
    - Standard operational user
    - Creates procurement documents (RFPA, Deal Slip, GRN)
    - Records operational data (Inward Register, Vehicle Dispatch, EOD Stock)
    - Can view documents and reports based on document-level permissions

  VERIFIER
    - First checkpoint in the approval chain
    - Reviews and verifies documents before they reach approvers
    - Assigned per document type via the Approval Flow configuration

  APPROVER
    - Reviews verified documents and gives approval or rejection
    - Up to 6 levels of approvers can be configured per document type
    - Each level can have single or double approval requirement
    - Decision options: Approved / Rejected / Query (sent back for clarification)

  FINALIZER
    - Final sign-off authority on approved documents
    - Two finalizer slots configurable (firstFinalizer, secondFinalizer)
    - Document is fully processed only after finalization

  SUPER ADMIN
    - Special role for data governance
    - Can soft-delete, restore, or permanently delete any document
    - Manages the recycle bin across all document types

Each user also has granular Document Permissions:
  canCreate | canView | canEdit | canDelete | canDownload
  (Configured individually per document type per employee)

Department classification for users:
  Admin | HR | Operations | Sale | Procurement | IT | Business Development |
  Exports | Branding & Marketing | Farming | Quality Checking | Other

--------------------------------------------------------------------------------
1.3 BENEFITS
--------------------------------------------------------------------------------

FOR THE BUSINESS:
  - Paperless Operations: All documents are created, approved, and archived
    digitally, removing physical paperwork entirely.
  - Multi-Company, Multi-Branch Support: A single platform manages all group
    entities and their respective branch locations.
  - Controlled Procurement: The RFPA → Deal Slip → GRN → AQR → Inward chain
    ensures goods are received only after proper authorisation.
  - Financial Accountability: Every payment (vendor/transport/labour/packing)
    is tracked via dedicated vouchers with approval trails.
  - Real-Time Stock Visibility: EOD stock reports, inward register, and
    inventory stock modules give live visibility into what is available where.
  - Compliance: GST fields, INR financials, and IST timestamps ensure
    the system is audit-ready and tax-compliant out of the box.
  - Target Tracking: Procurement and sales teams have weekly target vs.
    achievement tracking with dashboards.

FOR OPERATIONS TEAMS:
  - Approval notifications delivered in real time via Server-Sent Events (SSE)
    — no need to manually check for pending documents.
  - Document-level permissions ensure staff only see and act on what they are
    authorised for, reducing errors and data leaks.
  - Excel bulk-import for employee and product master data speeds up onboarding.
  - PDF generation for invoices, delivery challans, and vouchers — ready to
    print or share.

FOR MANAGEMENT:
  - Procurement Dashboard: Real-time view of purchase activity, vendor/farmer
    performance, and department-wise spend.
  - Management Dashboard: Cross-company performance overview.
  - Sales Dashboard: Order-to-invoice pipeline, outstanding payments, returns.
  - Full audit trail: Who created, approved, or modified every document and when.
  - User Activity Logs: Every login, logout, and CRUD action is recorded with
    IP address, device, and timestamp.


================================================================================
2. WORKFLOW
================================================================================

The system follows a structured procurement-to-payment and order-to-invoice
workflow. Each document moves through a defined sequence of states.

--------------------------------------------------------------------------------
2.1 PROCUREMENT WORKFLOW (Purchase Side)
--------------------------------------------------------------------------------

STEP 1 — REQUEST FOR PURCHASE APPROVAL (RFPA)
  - An employee raises an RFPA specifying the product, quantity, source
    (vendor or farmer), purchase location, and requesting department.
  - RFPA goes through the configured approval flow (Verify → Approve → Finalize).
  - Status: PENDING → APPROVED / REJECTED

STEP 2 — DEAL SLIP
  - Once the RFPA is approved, a Deal Slip is created from it.
  - The Deal Slip confirms the lot details, loading location, and special
    requirements for the purchase.
  - Deal Slip also goes through its own approval flow.
  - When approved, the GRN creation flag is enabled on the Deal Slip.
  - Status: PENDING → APPROVED / REJECTED

STEP 3 — GOODS RECEIPT NOTE (GRN)
  - When goods physically arrive, a GRN is created against the Deal Slip.
  - GRN captures: vendor/farmer, product quantities, vehicle number, bill image,
    freight charges, total amount, payment info, and receiving person.
  - GRN undergoes multi-level approval.
  - On approval, downstream document creation flags are enabled:
      isAQRCreated | isInwardCreated | isDumpCreated
      isMCVoucherCreated | isTPVoucherCreated | isPMPVoucherCreated | isLPVoucherCreated
  - Status: PENDING → APPROVED / REJECTED

STEP 4 — ARRIVAL QUALITY REPORT (AQR)
  - Quality team creates an AQR against the GRN to record the quality check
    results of the received goods.
  - Goes through its own approval.

STEP 5 — INWARD REGISTER
  - After quality approval, goods are formally entered into the warehouse
    via the Inward Register.
  - Inward type: Purchase | Transferred | Returned-by-Customer
  - Records gross/net quantities and inward cost.
  - Updates inventory stock.

STEP 6 — PAYMENT VOUCHERS (parallel to inward)
  Once a GRN is approved, the following vouchers may be raised in parallel:
  - Multi-Cash Voucher — for cash payments
  - Transport Payment Voucher — for vehicle/transport charges
  - Labour Payment Voucher — for unloading/handling labour
  - Packing Material Voucher — for packing material consumed
  Each voucher goes through its own approval before payment is released.

STEP 7 — DUMP REGISTER (optional)
  - If received goods are below quality threshold, a Dump Register entry
    is created to write off the wastage quantity.

--------------------------------------------------------------------------------
2.2 SALES WORKFLOW (Sell Side)
--------------------------------------------------------------------------------

STEP 1 — SALE ORDER
  - Sales team creates a Sale Order (PO) for a customer specifying products,
    quantities, billing/shipping details, and charges.

STEP 2 — DELIVERY CHALLAN
  Four types of delivery challans are supported:
  a) Customer Delivery Challan — for delivery to end customer
  b) Purchase Delivery Challan — for internal purchase transfers
  c) Stock Transfer Delivery Challan — for inter-branch stock movement
  d) Other Delivery Challan — miscellaneous dispatches

STEP 3 — VEHICLE DISPATCH REGISTER
  - Records the vehicle assigned for dispatch: driver, vehicle number, route,
    reaching time, client address, and transport billing.

STEP 4 — FINAL INVOICE
  - Invoice is generated against the Delivery Challan.
  - Includes: product amounts, GST (CGST/SGST/IGST), freight, discount,
    other charges, and total in words.
  - Amount Status: UNPAID → PAID (updated when payment is received)
  - PDF invoice can be generated and downloaded.

STEP 5 — RETURN BY CUSTOMER (optional)
  - Customer returns are processed and trigger a new Inward entry of type
    "returned-by-customer".

--------------------------------------------------------------------------------
2.3 APPROVAL WORKFLOW DETAIL
--------------------------------------------------------------------------------

Every document in the system goes through the following approval pipeline:

  DRAFT
    ↓  (employee submits)
  PENDING VERIFICATION
    ↓  (verifier reviews)
  PENDING APPROVAL — Level 1
    ↓  (first approver approves / rejects / queries)
  PENDING APPROVAL — Level 2 (if configured)
    ↓
  ... up to Level 6
    ↓  (final approver approves)
  PENDING FINALIZATION
    ↓  (finalizer signs off)
  APPROVED  ←→  REJECTED  ←→  QUERY (back to creator)

Approval modes:
  - Single Level: One approver at each configured level
  - Double Level: Two approvers at the same level (both must act)

Real-time notifications are pushed to the relevant approver via SSE as soon
as a document reaches their approval step.

SuperAdmin can soft-delete any approved/rejected document (moves to recycle
bin), restore it, or permanently delete it.

ARCHITECTURE EXPLANATION
--------------------------------------------------------------------------------

CLIENT LAYER
  The React/Next.js frontend communicates with the backend over HTTP/HTTPS.
  It is hosted on Vercel in production and runs locally on port 5173 during
  development. Multiple internal IP addresses are whitelisted as allowed CORS
  origins for LAN-based access.

NGINX REVERSE PROXY
  NGINX acts as the entry point to the system (port 8004). It:
  - Proxies all API requests to the Node.js app on port 4000
  - Serves static files (exports, uploads) directly without hitting Node.js
  - Enforces rate limiting to protect against abuse
  - Adds HTTP security headers (CSP, X-Frame-Options, X-XSS-Protection)
  - Handles gzip compression to reduce payload sizes
  - Supports up to 100MB file uploads (for Excel bulk imports and bill images)

NODE.JS APPLICATION SERVER
  The backend is built on Express.js using InversifyJS for dependency injection
  (IoC container). Every controller, service, and repository is registered as
  an injectable class, keeping the code loosely coupled and testable.

  Key responsibilities:
  - Route handling and request validation
  - JWT authentication and role/permission checks
  - Business logic execution (approval flows, stock updates, voucher creation)
  - Real-time notifications via SSE
  - PDF generation using Puppeteer and EJS templates
  - Excel report generation using ExcelJS
  - Scheduled cleanup via node-cron

POSTGRESQL DATABASE
  PostgreSQL 17 is the primary data store. TypeORM manages schema, migrations,
  and query building. All entities extend a base Model with UUID primary keys,
  soft-delete fields, and timestamp columns. The database stores all transactional
  data: employees, documents, approval flows, vouchers, inventory, etc.

REDIS CACHE
  Redis 7 is used for:
  - User data caching during login and token refresh (TTL: 5 minutes)
  - Token blacklist caching on logout (TTL: 1 hour) using SHA256-keyed entries
  - General query result caching (TTL: 60 seconds) to reduce PostgreSQL load

DIGITALOCEAN SPACES (S3-COMPATIBLE)
  All uploaded files (bill images, multi-upload documents) are stored in
  DigitalOcean Spaces using the AWS S3 SDK (multer-s3). Pre-signed URLs are
  generated for secure access.

SSE (SERVER-SENT EVENTS)
  The /sse/notifications endpoint maintains a persistent HTTP connection to
  each logged-in user. When an approval action occurs, the SSEService pushes
  a notification event directly to the relevant user's browser without polling.

INFRASTRUCTURE EXPLANATION
--------------------------------------------------------------------------------

HOST MACHINE
  The Node.js application server runs directly on the host machine (not inside
  Docker) and listens on port 4000. Docker containers communicate with it via
  the Docker Desktop gateway alias `host.docker.internal`. This design choice
  allows the app to be restarted independently without recreating containers.

NGINX CONTAINER (nginx_primefresh)
  Exposes port 8004 to the outside world. All incoming traffic — both API
  requests and static file downloads — enters through NGINX. It proxies API
  calls to Node.js and directly serves files from the /exports and /uploads
  directories, offloading that bandwidth from Node.js. NGINX also handles
  SSL termination if certificates are placed in the ./nginx/ssl directory.

POSTGRESQL CONTAINER (postgres_primefresh)
  Runs PostgreSQL 17 on internal port 5432, mapped to host port 6500 to avoid
  conflicts with any locally installed PostgreSQL. Data is persisted in the
  named Docker volume `pgdata`. The database is set to Asia/Kolkata timezone
  to ensure consistent timestamp storage. TypeORM migrations manage the schema.

REDIS CONTAINER (redis_primefresh)
  Redis 7 with AOF (Append-Only File) persistence enabled, meaning data
  survives container restarts. Password-protected with `redis123`. Used by
  the application for user session caching, token blacklisting, and general
  query caching. Data persisted in `redis_data` volume.

PGADMIN CONTAINER (pgadmin_primefresh)
  A web-based PostgreSQL administration tool accessible on port 9000.
  Used by developers to browse tables, run queries, and inspect the database
  schema. Data (saved connections, preferences) stored in `pgadmin_data` volume.

DOCKER NETWORK (primefresh_network)
  All Docker containers are connected on a single bridge network. This allows
  NGINX to reach Postgres and Redis by container name (e.g., `postgres_primefresh`),
  while the Node.js host app connects to Docker services via `localhost` with
  their mapped host ports (6500 for Postgres, 6379 for Redis).

DIGITALOCEAN SPACES
  Binary file storage (images, documents) is offloaded to DigitalOcean Spaces,
  an S3-compatible object store in Singapore (sgp1 region). This keeps the
  server filesystem lean and ensures files are accessible via CDN-backed URLs.
  Pre-signed URLs limit access to authorised requests.

LOGGING & MONITORING
